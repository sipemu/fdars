# fdars Performance Report

A single-threaded head-to-head of `fdars-core` against scikit-fda 0.10.1 and the
R FDA ecosystem (`fda`, `fda.usc`), before and after the v0.47.0 optimization
pass. Every number below is traceable to a committed CSV in
`benchmarks/results/` and the environment snapshot in `benchmarks/results/env.json`
— see [Methodology](#methodology) and [Reproduction](#reproduction) for the
exact commands that produced it.

## How to read this report

- **†** (dagger) — the fdars measurement failed the noise gate (RSD >= 5% or
  CI-width >= 5%). A daggered cell is never headlined as a confirmed win or
  loss, even when the raw ratio looks favorable.
- **Significant?** — "yes" means the two 95% confidence intervals are
  strictly non-overlapping (touching CIs count as "no"). Only a "yes" backs a
  speedup or regression claim; everything else is reported as a directional
  ratio with the caveat spelled out in prose.
- **Ratio semantics** — every `fdars vs X` ratio is `X time / fdars time`.
  A ratio at least 10% above 1.0 is "N× faster" (fdars wins); a ratio at
  least 10% below 1.0 is "N× slower" (fdars loses); anything within that
  +/-10% parity band is reported as "comparable", not as a win either way.
- **Single-threaded throughout** — every table in this report, and every
  reproduction command below, pins `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`,
  `MKL_NUM_THREADS`, `RAYON_NUM_THREADS`, `NUMEXPR_NUM_THREADS`, and
  `VECLIB_MAXIMUM_THREADS` to `1` on every side (fdars, scikit-fda, R). No
  table in this document reports a multi-threaded number; the `parallel`
  feature and rayon are discussed only qualitatively (see
  [Threading](#threading)).

- **FPCA has two R comparators.** `r_svd` is a hand-rolled, Simpson-weighted
  SVD port of fdars' own algorithm — it is the ecosystem-independent,
  hard-gated comparator (fdars-vs-R subspace cosine = 1.0 on every cell).
  `r_native_pca_fd` is R's own `fda::pca.fd`, which works in B-spline
  coefficient space rather than raw evaluation-point space; it is timed for
  ecosystem realism but is not gated (it was found in Phase 113 to diverge
  numerically from fdars at PC3–PC5 because of the coefficient-space
  smoothing, not because either implementation is wrong).
- **FPCR is a disclosed, not a gated, cross-library comparison.** scikit-fda's
  FPCR (FPCA scores → OLS) and R's `fda.usc::fregre.pc` are related but not
  identical algorithms; their correlation is reported per-cell in the table
  above for transparency, never used to pass/fail a run.
- **The FPCA quadrature convention differs by ecosystem.** scikit-fda
  integrates with the trapezoid rule; fdars and the R `r_svd` port both use
  Simpson's rule. This is disclosed (not hard-gated) for the fdars-vs-python
  FPCA comparison and is the reason that comparison's subspace cosine is
  below 1.0 while fdars-vs-R stays at 1.0 on every cell.
- **The `elastic` op is pairwise and N-independent by construction.** The
  harness always times a fixed 2-curve alignment regardless of the grid's N,
  so its row varies with M only — this is a property of what is being
  measured, not a claim about how `elastic_align_pair` scales with corpus
  size (see [N×M scaling](#nm-scaling) for the M-only exponent).

## Before/after vs the Phase 113 baseline

Read every table in this section as a **traceability record of what changed
between Phase 113 and Phase 116**, not as an optimization measurement (the
A/B tables above are the optimization measurement). Four things changed
between the two runs simultaneously, and this report does not attempt to
separate their individual contributions to any one row's delta:

- Phase 113 re-ran only `fregre_lm` and `functional_boxplot` live on the
  fdars side; every other fdars row in the Phase 113 baseline came from
  whatever criterion output already existed on disk at the time — of mixed
  vintage, spanning several earlier optimization phases.
- Those pre-existing baseline rows were measured under the default,
  multi-core rayon pool (no thread pinning). Several of the large deltas
  below on `elastic`/`karcher`-family groups are exactly this: losing
  rayon's parallelism between the baseline and a single-threaded re-run,
  not a regression in the underlying algorithm.
- Six benchmark groups present in the Phase 113 baseline no longer exist in
  the current bench files (`coclustering_co_cluster`, `face_covariance`,
  `fem_smooth`, `fpca_variants_fsvd`, `frechet_anova`,
  `fts_long_run_covariance`) — they are flagged `orphan` in the table below,
  not silently dropped.
- The Phase 116 after-run is thread-pinned end-to-end (all six
  `*_NUM_THREADS=1`), matching the cross-language harness's fairness
  contract.

The gate is fail-closed and runs BEFORE any timing is recorded for a cell —

as the Phase 112/113 baseline runs. fdars' own output is agreement-checked

binary, checked against R); for the other hard-gated ops the gate checks
that scikit-fda and R agree with each other, which is a weaker but still
meaningful signal that the op is being compared fairly.

### Timing statistics and noise gate

Each ecosystem reports a different timing statistic, by design of its own
idiomatic benchmarking tool: fdars uses criterion 0.5's mean with a 95%
bootstrap confidence interval; scikit-fda uses Python's `timeit` mean over a
fixed repeat count per op (50 repeats for `fpca`/`basis_smoothing`/
`depth`/`functional_boxplot`/`fpcr`; 10 repeats for the pairwise `elastic`
op, since it is heavier per call); R uses `bench::mark()`'s median over a
fixed iteration count per op (10 iterations for the same five ops; 5
iterations for pairwise `elastic`). Python and R therefore carry no
confidence interval — they report one point estimate per cell, which is why
the before/after control table above reports drift as median/max percent
change rather than a significance test. The noise gate (shared with
`hotspot_ranking.md`, never redeclared) fails a criterion row when its
relative standard deviation is >= 5% or its CI width is >= 5%; it is the
only gate applied to fdars rows and has no equivalent for the single-sample
Python/R rows. Significance for any comparison is always the strict
non-overlapping-CI test; the ratio-label parity band is +/-10%.

### Data parity

The grid-aligned fdars bench (`fdars-core/benches/crosslang_grid.rs`) reads
the exact same seeded CSVs the Python and R runners read, and hard-fails
(`FDARS_CROSSLANG_REQUIRE_CSV=1`) rather than silently falling back to a
different random draw when the harness invokes it. A standalone
`cargo bench` run (no harness) instead falls back to a deterministic
`StdRng(42)` generator, so the bench is still runnable in isolation but never
silently mismatched against the cross-language CSVs when it matters. Legacy,
non-grid-aligned criterion ids (the `audit_*`/`perf_*` benches used in the
before/after tables above) use their own in-bench generators and were never
intended to share data with the cross-language harness.

### Threading

All six `*_NUM_THREADS` environment variables are pinned to `1` for every
ecosystem in every table in this report. With the default `parallel`
feature enabled, fdars uses rayon for multi-core execution outside of this
report's fairness-first, single-threaded measurements — that capability is
real and shipped, but deliberately not tabulated here (D-12), because a
multi-threaded fdars number next to single-threaded Python/R numbers would
not be a fair comparison. The four `audit_p5_*_threads`/
`perf_parallelism_*` benchmark groups exist specifically to explore
thread-scaling and are excluded from every table above.

## Reproduction

The full re-run this report is based on can be reproduced end-to-end from a
clean clone:

1. Clone the repository:

   ```bash
   git clone https://github.com/sipemu/fdars.git
   cd fdars
   ```

2. Install a Rust toolchain matching the [Environment](#environment) table
   above (the `linalg` feature needs Rust 1.84+; the `crosslang_grid` bench
   itself only needs the workspace MSRV):

   ```bash
   rustup toolchain install 1.97.0
   rustup default 1.97.0
   ```

3. Create the Python virtual environment and install the pinned harness
   dependencies:

   ```bash
   python3 -m venv benchmarks/.venv
   benchmarks/.venv/bin/pip install -r benchmarks/requirements.lock
   ```

4. **Python 3.14 only:** apply the `multimethod` metaclass patch (see
   `benchmarks/README.md`'s "Python 3.14 multimethod patch" section for why
   this is needed):

   ```bash
   patch -p1 -d benchmarks/.venv/lib/python3.14/site-packages \
       < benchmarks/patches/multimethod-2.1-py314.patch
   ```

5. Restore the R packages from `benchmarks/renv.lock`, then verify them
   (see `benchmarks/README.md` for the exact `renv::restore()` invocation
   and why `.Rprofile`/`renv/` are gitignored and not auto-activated on a
   clean clone):

   ```bash
   Rscript -e "renv::restore()"
   Rscript benchmarks/r_deps_check.R
   ```

6. Run the single end-to-end reproduction command:

   ```bash
   benchmarks/.venv/bin/python benchmarks/run_all.py --full
   ```

   The default 540s per-chunk / per-cell bound matches the published run
   exactly (7 heavy single-threaded elastic/Karcher chunks are expected to
   time out under it — see
   [Before/after vs the Phase 113 baseline](#beforeafter-vs-the-phase-113-baseline)).
   Pass `--timeout-s 0` to remove fdars' per-chunk bound entirely and
   measure the cells the published run recorded as timeouts (this will take
   substantially longer — budget accordingly).

7. Render the report and verify it against the committed inputs:

   ```bash
   benchmarks/.venv/bin/python benchmarks/render_report.py
   benchmarks/.venv/bin/python benchmarks/render_report.py --check
   benchmarks/.venv/bin/python benchmarks/render_report.py --check-prose
   ```

## Known limitations and disclosures

- **Background desktop load was present during part of the fdars re-run**
  (1-minute load average 2.8–15.0 at scheduler-call starts, despite a
  passing quiet-machine check before the run started) — see
  [Environment](#environment) for the full disclosure. The heavier load
  overlapped the fdars measurements, so any bias most likely runs against
  fdars (slower), not in its favor.
- **Timeouts and orphans are disclosed, not hidden.** 7 heavy
  single-threaded elastic/Karcher chunks did not complete inside the 540s
  bound (4 direct timeouts, 3 inferred from a cheaper sibling in the same
  group timing out) and are listed by criterion id in the
  "Baseline rows not re-measured" table above; 6 legacy benchmark groups no
  longer exist in the bench files and are flagged `orphan` in the same
  table, not silently dropped from the report.
- **The Phase 113 baseline is of mixed vintage and mostly not thread-pinned**
  — only `fregre_lm` and `functional_boxplot` were re-measured live in
  Phase 113; every other baseline row is on-disk criterion output from
  whatever optimization phase last touched that bench, measured on the
  default multi-core rayon pool. The before/after tables above are a
  traceability record against that baseline, not an optimization
  measurement.
- **fdars' own output is agreement-checked against another ecosystem for
  FPCA only.** For the other hard-gated ops the gate checks scikit-fda
  against R, not fdars against either — see
  [Numeric agreement gate](#numeric-agreement-gate).
- **FPCR is a disclosed, not gated, cross-library comparison** — scikit-fda's
  FPCA→OLS and R's `fda.usc::fregre.pc` are related but not numerically
  identical algorithms.
- **The R FPCA timing shown as the hard-gated comparator is a hand-rolled
  Simpson-weighted SVD port**, chosen because it agrees with fdars at
  subspace cosine 1.0; R's own native `fda::pca.fd` (B-spline coefficient
  space) is timed separately and shown alongside it, never conflated with
  it.
- **The Python 3.14 harness venv needs an in-place metaclass patch** to
  `multimethod/__init__.py` before scikit-fda will import; the patch file
  is committed at `benchmarks/patches/multimethod-2.1-py314.patch` and its
  provenance (pristine wheel hash matches the venv's own `dist-info/RECORD`
  entry) is documented in `benchmarks/README.md`.
- **Single machine, single run.** Every number in this report comes from one
  run on one machine (see [Environment](#environment)); it is not a
  statistical claim across hardware or repeated runs, though the noise gate
  and confidence intervals bound the uncertainty of any one criterion cell.
- **scikit-fda is this milestone's functionality yardstick, not its
  performance yardstick's peer in scope.** This report covers performance
  only — a separate audit (Phase-numbered elsewhere in this milestone's
  history) covers functionality-gap analysis against scikit-fda; the two
  should not be conflated.
